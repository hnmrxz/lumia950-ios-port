## Handset

- Boot chain, its four corrections and the procedure that matches the evidence live in
  `docs/hardware/handset-boot-chain.md`; this page does not repeat them.
- **Deployment and rollback are rehearsed offline.** `scripts/rehearse-phone-install.py` runs the
  installer's dry run, then the runbook's single install-and-verify command against a reference store and
  against a drifted one; `scripts/rehearse-phone-rollback.py` snapshots a synthetic EFIESP, damages the
  store, proves the dry run writes nothing, and proves `--apply` restores and verifies it. The procedure
  they back is `docs/hardware/post-unlock-runbook.md`.
- The boot store is checked in three layers, in the order the firmware sees them: `{bootmgr} path` must be
  `\efi\boot\bootarm.efi`, `{bootmgr} default` must name an entry, and that entry must be the MainOS shim
  (`scripts/check-bcd-layout.py`). `phone-install.py --verify-bcd <enum>` runs that check in the same
  command as the install and fails the install when the store disagrees.
- **The chain now boots on the handset.** After the Windows-on-ARM deployment was applied, the phone walked
  firmware -> `bootarm.efi` -> the deployment tool's ARM32 `BootShim.efi` (subsystem 0x10) -> its `UEFI.elf`
  (LumiaWoA 2.16385) -> `EFI\BOOT\BOOTAA64.EFI` (this port's loader) -> the UniXNU 0.1.0 menu ->
  DarwinBoot's hand-off, with the kernel read from MainOS through the staged NTFS driver and the real panel
  reported as 1080x1920, row 4320 bytes, 32 bpp at 0x400000. Measurements, including the two failures that
  preceded it, are in `docs/hardware/2026-11-26-first-hardware-boot.md`.
- `XNU-entry-tested` is **not** claimed for the handset: no kernel line had been observed after the hand-off
  when that note was written.
- `--unique-chip-id` in the handset ADT is still a zero placeholder
  (`docs/hardware/2026-11-24-device-identity.md`).
- Recovery is either an FFU flash (`scripts/phone-recover.ps1`, donor FFU for the unlock) or a snapshot
  restore (`scripts/phone-snapshot.py`); an FFU cannot be generated by the tooling
  (`docs/hardware/2026-11-25-flashing-toolchain.md`). The four recovery scripts are parsed by the real
  PowerShell parser in `scripts/check-powershell-parses.py`, so a syntax error cannot hide there.

## Boot chain preservation and the MainOS question (audit, 2026-11-27)

The chain that works on the handset is recorded in `docs/hardware/boot-chain-preservation.md`, together with the files that must
never be replaced (`EFI\boot\bootarm.efi`, `\UEFI.elf`, `EFI\Microsoft\BOOT\BCD`) and the rollback each change has.

The audit found three records that disagree with the phone as it is today, and they matter because two of them are the inputs to a
recovery:

* `install-native-bringup.py`'s `CRITICAL` table expects `bootarm.efi` `e0034756...` and `BOOTAA64.EFI` `b782ee89...`, while the
  handset carries `f259543a...` (870,856 bytes) and this port's loader `9d9311b3...`. The installer therefore refuses to run, which
  is the safe outcome; it also means it cannot be used until the table is re-baselined from a measured state.
* `2026-11-25-unlocked-partition-images.md` records the EFIESP image as 16,777,216 bytes / `1e9b2ff3...`; the file on disk is
  33,554,432 bytes / `e72bb27d...`. The MainOS image does match its record. Restoring the EFIESP image without re-checking would be
  restoring something whose identity is not established.

`docs/hardware/unlock-partition-dependencies.md` states the conclusion that governs the MainOS plan: the unlock patches live on
both EFIESP and MainOS, the two must be restored together, and **no per-file or per-sector inventory of those patches exists**. So
formatting MainOS is an irreversible step whose damage cannot be bounded, and the reversible alternatives (microSD, a directory on
the existing NTFS volume) are the ones to prove first.

`docs/hardware/mainos-replacement-readiness.md` separates the two questions the plan conflates: changing *where the payload lives*
is cheap and reversible (the NTFS read path already works and a FAT32 volume on microSD can be proven without touching MainOS), while
an **APFS root** needs a block device driver in the kernel, a working kext delivery path and the real root-matching rule -- none of
which exist yet. `Apple_HFS` is the emulator fixture's expectation, not a property of the pinned kernel (which has no HFS+ at all).

## The objective, restated (2026-11-27)

The finish line is not the Apple logo, not a kernel log line and not the DarwinBoot hand-off:

> Lumia 950 (Talkman / MSM8992) boots XNU, reaches BSD initialisation, reads the eMMC **read-only** through XNU's own storage stack,
> parses the GPT, identifies the APFS container and mounts an APFS root, and stays running.

`docs/hardware/bringup-milestones.md` is the authority for how that decomposes (M1 BSD initialisation, M2 eMMC controller and block
device, M3 read-only GPT, M4 APFS container and volumes, M5 APFS root and userland), with the evidence each milestone needs and the
rule that none can be skipped. The microSD payload experiment is an auxiliary check of an alternative payload volume, and formatting
MainOS is not a prerequisite for any of the five milestones.

As of this note M1 is **not** met: the handset shows the loader's hand-off page and then nothing, which after the measurements in
`docs/hardware/2026-11-27-handset-handoff.md` means the kernel stops before `arm_vm_init` -- a point where the kernel has no
framebuffer mapping and cannot print. The two candidate observation routes are written in the milestone document, with the rule that
route A (a mapping made from the kernel's own bootstrap page tables) is prototyped in QEMU first.

One engineering requirement from the same review is now enforced by a test: read-only access has to hold in the driver layer, not by a
mount option. `scripts/test-storage-read-only.py` refuses any change that would add a write or erase command to `NativeSdhci`, that
would forward an outbound transfer, or that would stop reporting write protection.

## M1 observation: where it stands

Both QEMU configurations reach root-wait on artifact `d57f6eea` (commit `d51be80`) with ESR 0x0, and the early marker reports its own
refusal through the post-VM console: 4 without the boot argument, 7 with it, meaning the fixed L1 slot was already taken and nothing was
drawn. The mapping is therefore not installed and proves nothing about the handset yet.

The attempt that would have installed it -- filling the highest empty L1 entry -- removed the console entirely (build 45969556167), so
entries cannot be added to the bootstrap tables without understanding how `arm_vm_init` consumes them; that read is the next step, not
another slot. The submodule blocker that stopped every build is repaired in CI: `drivers/NativeMetal` is re-pointed to the remote's head
only when its recorded commit is really gone, and the substitution is printed. Details in `docs/hardware/m1-observability.md` section 11.

## Host tests must run on the CI host, not just here

A test added on 2026-11-25 asserted that a `C:\...` literal was absolute. That is true on Windows and
false on the Linux `validate` host, so it turned the job red the moment it was pushed. The same class of
bug came back on 2026-11-26, from the other side: `phone-snapshot.py` built its mount root as
`Path(value.rstrip("\\") + "\\")`, which only makes sense for `R:` and produced a non-directory on POSIX
(run 45711382502, `save exit: 2`). `mount_root()` now adds the separator only for a drive-letter form, and
the rehearsal that caught it runs on both hosts. `scripts/check-host-tests-portable.py` still reads every
test file and refuses a Windows absolute path inspected through `Path`/`open` instead of
`PureWindowsPath`; forty test files are clean.
