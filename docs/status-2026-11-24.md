## What runs

- The iOS chain builds: the `kernel` job is green with the pthread component linked
  (run 45314032032, and again 45318161131). The gate in `scripts/check-kernel-link.py` asks for the
  component's global symbols because the linker emits its entry point as a non-external
  `__startup_EARLY_BOOT_entry_source_pthread_bootstrap_NN` that `nm -gU` cannot show.
- The emulated boot crosses `bsd_init`: the archived report records `past_bsd_outcome: stopped`, the
  dmesg reaches `dlil_init`, and `_vfs_mountroot` was never reached.
- It then stops inside `skmem_sysctl_init` (`fault_elr_symbol` in the report). The store is
  `sysctls->version`, `sysctls` comes from the static `sk_sys_obj`, and `skmem_init` both allocates
  that object and calls the sysctl initialiser, with a panic if the allocation failed -- so the
  object exists and the address it points at is not mapped in this port's kernel VA layout.
  `skmem_region_init` takes its segment sizes from boot arguments (`skmem_seg_size`,
  `skmem_md_seg_size`, `skmem_drv_buf_seg_size`, `skmem_usr_buf_seg_size`), which is the thread to
  pull next.
- The handset side is installed and verified: EFIESP carries the UniXNU loader as `bootarm.efi` (the
  stock one is `bootarm.efi.stock`), the menu configuration with an `xnu` entry, DarwinBoot and the
  EfiFs NTFS driver; MainOS carries the 56,619,008-byte prelinked kernel with its ADT. `check-payload`
  accepts the assembled tree.

- No handset boot has been observed yet. The first attempt showed **"press any key to shutdown"**,
  which is the firmware's mass-storage prompt: with USB attached at boot the loader is never run, so
  that attempt tested nothing.
- `--unique-chip-id` was not available, so the ADT on the phone was generated with zeros. Any kernel
  result from the handset has to be read with that in mind.
- The desktop is not close: `vfs_mountroot` has not been reached in the emulator, and no iOS userland
  is staged anywhere.

## Evening update: what is installed, what is blocked, and why

page: docs/hardware/handset-boot-chain.md consolidates the install notes that used to be spread over
eight files.

Three things cannot be settled from this session, and they are environment boundaries rather than
engineering problems:

- **No boot has been observed.** The one attempt showed "press any key to shutdown", the firmware's
  mass-storage prompt, which runs instead of the loader when USB is attached at boot. The test that
  answers the question is: unplug, power on, watch the panel for 30 s.
- **The offline registry cannot be read.** `reg load HKLM\OfflineSys F:\Windows\System32\config\SYSTEM`
  answers `A required privilege is not held by the client`, so the handset's chip identifier cannot be
  fetched that way. The ADT installed on the phone still carries the zero placeholder.
- **The BCD cannot be read or edited either.** `bcdedit /store F:\EFIESP\EFI\Microsoft\BOOT\BCD /enum all`
  answers `Access is denied`. Writing files to EFIESP works, but this tool needs a higher token. If the
  firmware turns out not to launch `EFI/boot/bootarm.efi`, the BCD route needs one elevated command from
  the owner before it can even be inspected.
